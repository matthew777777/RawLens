◆ Top finding: they don't make Adreno zero-copy work harder — they avoid the
  Adreno-hostile import entirely on most streams. Only RAW_SENSOR is
  zero-copied, and only as a sampled image; everything else is a CPU-plane
  upload. We zero-copy RAW_SENSOR as a storage buffer from a non-GPU allocation,
  which Mali tolerates and Adreno silently reads as zeros/black.

  ┌─────────────────┬────────────────────────────┬─────────────────────────────┐
  │ Aspect          │ Unspektrawesome            │ RawLens VF                  │
  ├─────────────────┼────────────────────────────┼─────────────────────────────┤
  │ Zero-copy input │ VkImage R16_UINT, SAMPLED  │ VkBuffer SSBO, byte math    │
  │ Reader usage    │ USAGE_GPU_SAMPLED_IMAGE    │ No GPU usage (4-arg)        │
  │ RAW10/RAW12     │ CPU plane → memcpy         │ Not offered, RAW_SENSOR     │
  │                 │ VkBuffer                   │ only                        │
  │ BLOB AHB        │ Rejected, stream           │ Imported as buffer anyway   │
  │                 │ blacklisted                │                             │
  │ Output          │ Swapchain present directly │ AHB storage image → EGL     │
  │                 │                            │ re-import                   │
  │ Fallback unit   │ Per-stream                 │ Per-session tier latch      │
  │                 │ (route/format/size)        │                             │
  └─────────────────┴────────────────────────────┴─────────────────────────────┘

  Why Adreno breaks for us specifically:

  1. Allocation mismatch. Their
     /tmp/unspektra/Unspektrawesome-source-main/app/src/main/java/com/unspektraw
     esome/camera/session/Camera2RawSession.java:834 creates the RAW_SENSOR
     reader with USAGE_GPU_SAMPLED_IMAGE, so gralloc allocates a GPU-shareable
     allocation. Our
     app/src/main/java/com/matthew/rawlens/RawCameraController.kt:910
     deliberately omits it — adding it starved the MT6878 HAL — so on Adreno the
     buffer was never allocated for GPU data access. Our own comment in
     app/src/main/java/com/matthew/rawlens/VfVulkan.kt:10 records the symptom:
     import succeeds, reads back zeros on Adreno 750, lock+memcpy works. Mali's
     unified gralloc hides this; Adreno doesn't.
  2. Buffer vs image import. Their
     /tmp/unspektra/Unspektrawesome-source-main/app/src/main/cpp/VulkanRenderer.
     cpp:1563 requires a 2D non-BLOB AHB, vkFormat == VK_FORMAT_R16_UINT, and
     SAMPLED_IMAGE feature, creates it OPTIMAL tiling, and reads via
     usampler2D/texelFetch. Our app/src/main/cpp/vf_vulkan_vf.cpp:893 imports
     allocationSize bytes as an SSBO and does y*pitch+x addressing, assuming
     linear CPU layout — false for Adreno tiled allocations.
  3. Fallback is structural, not probed. A rejected import is classified in
     /tmp/unspektra/Unspektrawesome-source-main/app/src/main/java/com/unspektraw
     esome/preview/RawImportCapability.kt:28, that stream is marked
     INCOMPATIBLE, and
     /tmp/unspektra/Unspektrawesome-source-main/app/src/main/java/com/unspektraw
     esome/preview/RawPreviewPlanSelector.kt:25 re-plans to RAW10/12 upload. We
     instead need the black-output probation in
     app/src/main/java/com/matthew/rawlens/RawViewfinder.kt:1906 to detect
     silent zeros, and the newer BguViewfinder path only calls computeNative —
     it never calls the working computeCopyNative tier.

  They also enumerate all GPUs requiring compute+present+AHB+foreign+float16 in
  one family, and special-case Adreno <700 workgroup size to 16×8 — evidence
  they tested on Adreno rather than assuming Mali behavior generalizes.

  The stealable fix is not a barrier tweak: give the VF its own GPU-sampled
  RAW_SENSOR reader trial, import as R16_UINT sampled image, and on rejection
  fall back to a RAW10/12 CPU-plane upload session instead of forcing the shared
  ZSL reader's buffers through SSBO import.

  will work for us
