# MGC 9.8 RAW finishing audit and RawLens Vulkan design

## Decision

Build a bounded Vulkan still-finishing path that shares RawLens's scene-referred math and feeds the native CPU encoders directly. Begin with SDR JPEG and measure the output handoff independently of image-quality changes. For image quality, prioritize noise-aware local exposure, highlight color and texture retention. JPEG and JPEG XL should share the upstream scene processing and diverge at their output transforms, packing and encoding.

Scope begins with one RAW frame, a merged CFA mosaic, or merged scene-linear RGB. It ends at successful publication of the JPEG or JPEG XL. Alignment, capture policy and merge algorithm changes are outside this finishing comparison, though end-to-end tests also measure the user's wait from shutter.

## Current RawLens path and cost

- [RawDevelopmentCoordinator](../../app/src/main/java/com/matthew/rawlens/RawDevelopmentCoordinator.kt) handles single and merged CFA, linear RGB MFSR and monochrome. Its selectable Vulkan RCD feeds GLES still finishing. AMaZE, Quad Bayer and existing highlight paths provide quality and compatibility references.
- [Gles31JpegOutputProcessor](../../app/src/main/java/com/matthew/rawlens/Gles31JpegOutputProcessor.kt) already has a fused display path, but the save path still reads back RGBA and copies it into a full-size Bitmap. [Native JPEG](../../app/src/main/cpp/native_jpeg_encoder.cpp) accepts the Bitmap and writes libjpeg-turbo scanlines. At 4000×3000 those two RGBA8 representations total roughly 92 MiB if both are live. At 50 MP they total roughly 381 MiB. These are logical pixel sizes, excluding GPU output, RAW input and encoder allocations.
- [Gles31JxlOutputProcessor](../../app/src/main/java/com/matthew/rawlens/Gles31JxlOutputProcessor.kt) contains a full-frame RGBA half-float readback. That representation alone costs about 92 MiB at 12 MP. [Native JPEG XL](../../app/src/main/cpp/native_jxl_encoder.cpp) supplies a whole image and accumulates the encoded output. The vendored encoder contains chunked input and output-processor APIs. The vendored implementation buffers input when streaming is unavailable, so verify actual allocations for each mode. [libjxl encoder API](https://libjxl.github.io/libjxl/api_encoder.html)
- [DevelopQueueService](../../app/src/main/java/com/matthew/rawlens/DevelopQueueService.kt) currently imports DNG into either a linear RGB buffer or a CFA float array and goes through the JPEG Bitmap path. Camera and offline/Merges output need to converge on the new backend while retaining their respective metadata and publication behavior.
- The [older JPEG study](jpeg-pipeline-study.md) reported 11.5–19.2 s GPU development and 0.37–0.50 s JPEG save on one 12 MP build. These are historical measurements. Fresh traces should separate highlight reconstruction, demosaic, display, transfer, codec and publishing on the current checkout.

## Implementation order

1. **Establish parity and measure the handoff.** Add a native still-export entry behind the coordinator, initially with fixed settings and a known scene buffer. Share existing display-transform definitions and verify against the current GLES output with identical input, precision, orientation, dither seed, gamut and transfer. Have Vulkan write encoded RGB8 into two reusable host-visible strip slots. Feed libjpeg-turbo scanlines through a file descriptor, keeping 4:2:2 and 4:4:4, ICC, EXIF, orientation and transactional publishing. Use small asymmetric/odd-size fixtures before phone timing. Keep Ultra HDR routing through the existing writer until the strip path can emit and verify a matching base and gain-map pair. [libjpeg-turbo API and raw data requirements](https://github.com/libjpeg-turbo/libjpeg-turbo/blob/main/doc/libjpeg.txt)
2. **Move scene development to Vulkan.** Make the input type explicit: CFA code values plus black/white, crop phase, lens shading, noise model and calibration, or scene RGB with documented primaries, scale and already-applied corrections. Normalize on GPU from packed RAW or compact 16-bit staging where the input permits. Reuse still RCD math, with MHC as the low-cost reference and AMaZE as the high-detail reference. Keep Quad and mono distinct, and bypass demosaic on merged RGB. Apply camera color and white balance exactly once. Preserve negative and above-white scene values where the existing math requires them. Use FP32 for matrix and reduction math initially and qualify FP16 storage per stage/device. Reuse existing highlight reconstruction as a reference, then implement GPU clip-mask compaction and bounded halo-expanded work. For widespread clipping cap expensive recovery and use a measured full-frame fallback. [Published MHC stencil](https://www.ipol.im/pub/art/2011/g_mhcd/)
3. **Improve the picture before adding a model.** Build a small log-luminance analysis image from provisional scene RGB. Compute robust global exposure plus an edge-aware low-resolution gain field with limited lift in noisy shadows, preserved highlight headroom and bounded local gradients. Apply the gain in scene-linear space before RawLens's chosen display transform. Reuse the existing BGU slice concept and compare a deterministic bilateral grid against a fast local-Laplacian reference. Use RAW noise variance and merge confidence when available to gate chroma/luma cleanup and sharpening; when confidence is absent, use noise and detail statistics. Test false color on repeating texture, shadow stability, hue under partial clipping, haloing and skin tones. Enable tile/ROI detail recovery only when the fast path leaves a measurable defect. [Fast Local Laplacian Filters](https://imagine.enpc.fr/~aubrym/projects/llf/index.html) · [Deep Bilateral Learning](https://groups.csail.mit.edu/graphics/hdrnet/)
4. **Optimize the JPEG and JXL branches independently.** Compare RGB scanlines with GPU planar YCbCr plus `jpeg_write_raw_data`. If the planar path wins, implement full-range JPEG coefficients, matched chroma downsampling and DCT/MCU padding, including odd sizes. Avoid GPU DCT and entropy work until the existing codec is measured as the dominant cost. For JXL, offer the current precision/profiles through packed RGB without alpha; test existing whole-frame mode against chunked input plus streaming output. JXL requests rectangles, so use a bounded rect cache or measure a disk-backed staging variant; a FIFO sufficient for JPEG cannot guarantee JXL's access pattern. Sweep effort, thread cap, quality and pixel format, and report memory for both lossy and lossless modes. Preserve current color/transfer and Exif/XMP semantics. [libjxl encoder API](https://libjxl.github.io/libjxl/api_encoder.html)
5. **Consider a tiny learned residual after the deterministic path passes.** If backlit subjects or difficult mixed light still lose blind comparisons, train an in-house low-resolution scalar gain/detail predictor on paired scene-referred input and target renders with appropriate rights. Retain the deterministic base, clamp the residual and apply it through the existing Vulkan slice. The HDRNet paper and public code are design references. The APK findings provide comparison evidence. [Public HDRNet implementation](https://github.com/google/hdrnet)

For mobile compute, prototype 16×8 and 16×16 workgroups and sweep strip heights of 32, 64 and 128 rows separately. Load neighborhood halos once where it reduces traffic, compute only valid tile interiors, and keep crop phase, lens shading and noise coordinates global. Inspect spills, occupancy and actual memory traffic on Adreno and Mali. Broader or global analysis should run once on the smaller image. Avoid intermediate full-resolution RGB where producer and consumer can share a tile; account for any full-size scene image the caller still owns. Use one reusable native working set, explicit host visibility/invalidation and per-slot completion. Start with one active finish per device and overlap a GPU strip with CPU encoding. Check preview pacing and background CPU contention before increasing concurrency. At 4000 px wide, two 64-row RGB8 output slots total about 1.46 MiB before stride alignment. The input, live GPU scratch and codec heap sit outside this estimate.

## What counts as beating MGC

- **Finishing comparison:** Use identical merged DNGs from the public HDR+ dataset and identical RAW captures for RawLens version-to-version checks. Use the published reference JPEGs as historical quality comparators. If this APK can accept identical RAW inputs through a verified path, add that as a separate comparison. Otherwise compare MGC using matched repeated captures on the same device, checking lens, exposure, focus, resolution and scene motion. Report this separately because capture and merge can influence the outcome.
- **Image quality:** Test daylight/high contrast, tungsten/mixed light, backlit faces across skin tones, low-light motion, signs/foliage/fabrics and clipped LEDs or speculars. Compare matched display profiles, framing and output size. Use paired blind full-image and crop reviews, with chart checks for neutral/color error, overshoot, texture and false color. For output-path parity use decoded pixel tolerances and metadata validation. For JPEG XL compare at matched perceived quality and list file size and latency separately.
- **Daily use:** Trace RAW-ready to MediaStore publication and shutter to publication separately. Collect p50/p95 and failures across cold start, warmed idle, and a fixed-cadence 20-shot sequence on matched Adreno and Mali devices where available. Record GPU timestamp spans, full-job wall time, peak CPU RSS/PSS and owned Vulkan allocations without double-counting shared mappings, preview frame pacing, energy per photo where measurable, and thermal throttling. Include 12 MP and high-resolution modes with edge sizes and JPEG/Ultra HDR/JXL decode checks.
- **Prototype gates:** Target at least 2× faster warm median development than the current RawLens path and at least 30% less peak incremental memory for 12 MP SDR, while retaining quality and metadata under the same settings. These are proposed goals pending baseline. For a claim against MGC, require better blind preference in difficult scenes and competitive p95 shutter-to-save, energy and memory on the same phone. Publish per-scene results and any tradeoffs. A single workstation or APK analysis cannot verify these gates.
