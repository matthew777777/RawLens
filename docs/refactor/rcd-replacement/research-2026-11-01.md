# Public-source RCD research and recommended next steps

Date: 2026-11-01. Research only: no replacement shaders/native code were written,
no device tests were run, and no commits or remote changes were made by this
research task. Do not reopen the private disputed-source archives for this work.

## Recommendation

Build an explicitly attributed GPL-3.0-or-later port of a pinned RawTherapee RCD
implementation, with independently designed GPU storage, tiling and Android
integration. Treat current photo RCD as a compatibility candidate and regression
comparison, not the sole correctness oracle. Preserve the current photo path
until the replacement earns equivalence. Use the existing plan's provenance,
correctness, packing and integration gates, with the refinements below.

This is a public-source port and our optimization work, not a strict clean-room
certification or exclusive ownership of RCD. Naming or a new session does not
change prior exposure. The unresolved historical-distribution issue is separate.

## What the GPU references establish

The vkdt source has a directional/low-pass prepass followed by a reconstruction
kernel using shared R/G/B arrays and workgroup barriers. Its host graph keeps
VH full-size and PQ/LP at half width. This supports investigating local
reconstruction as an alternative to repeated full-frame RGB intermediate I/O.
It does not establish mobile throughput, numerical equivalence to RawTherapee,
or correctness of copying its workgroup/halo settings into our implementation.

In particular, the inspected vkdt directional prepass accumulates responses
before squaring, while the inspected RawTherapee code combines squared
responses. Its reconstruction uses FP16 shared storage and explicit clamps.
Those are material algorithm/precision differences, not just syntax. Its
1024-invocation default is described in terms of desktop hardware; query mobile
limits and select our own workgroup sizes. Derive halos from our dependency DAG.

The vkdt README declares BSD-2-Clause for its own code with GPLv3 exceptions
and separate dependency licensing. The inspected RCD files do not each supply a
complete per-file origin/license chain. Do not assume a repository-wide default
licenses every upstream-derived RCD expression under BSD. Prefer the clearly
attributed RawTherapee source for the port and record/resolve provenance before
copying any vkdt implementation. Architectural comparisons do not require
copying its code.

## Photo path findings that affect the starting point

1. `vf_rcd.comp` carries a RawTherapee attribution and has a pre-dispute history.
   It is an integration asset we can investigate; its header alone does not
   establish exact equivalence or a complete provenance record.
2. The inspected upstream CPU implementation clips normalized CFA to [0,1],
   clamps final negative output, and calls a separate nine-pixel border routine.
   RawLens mirrors edges and supports float CFA above sensor white in its photo
   path. Preserve/document those application extensions separately from the
   canonical upstream test domain; do not claim complete upstream border/HDR
   bit parity.
3. `RcdReference.kt` mirrors once, whereas the GPU helper includes repeated
   reflection for tiny dimensions. Its top comment still says clamp-first.
   Define supported minimum dimensions and small-image handling explicitly.
4. Existing device parity gates include mean error 0.005 and max error 0.05;
   submission helpers can also use test assumptions that skip unavailable
   paths. These tests are useful regressions, not proof of strict mathematical
   equivalence or universal shader correctness. A new required-path test must
   fail rather than skip when its advertised supported path malfunctions.
5. The shader reconstructs into `img_rgb` while reading neighboring values from
   the same image. The comment calls unchanged-channel writeback value-benign.
   Audit overlapping whole-texel accesses against Vulkan's memory rules. Use
   distinct immutable inputs/output images or genuinely non-overlapping scalar
   buffers in the new baseline; do not rely on identical stored values to prove
   absence of a race. This is an identified audit concern, not a completed GPU
   fault diagnosis.

## Proposed implementation progression

### M1 — Provenance plus an independent host oracle

Extract only the pinned public algorithm dependency closure with original
notices, exact source hashes, an adaptation patch and reproducible build flags.
Keep an upstream-derived C/C++ scalar oracle independent of our Kotlin/GLSL
translation. Feed explicitly normalized CFA and compare stage values as well as
final RGB. Freeze interior behavior, border policy, CFA phase and numeric domain.

Use synthetic/appropriately licensed fixtures covering four Bayer orders, crop
phase, asymmetric ramps, color edges, flat fields, zeros, saturation, noisy
texture, odd widths/strides, tiny images and frame-to-frame parameter changes.
Maintain a separate above-white/HDR extension suite. Document initial
absolute/relative/ULP expectations before optimizing; never loosen a limit just
because the optimized path fails. Do not require cross-device universal bit
identity for floating-point math.

Deliver the provenance manifest, traceability table, host oracle, fixture
manifest and explicit numerical contract first. This is the recommended next
implementation task. It does not require Android device testing.

### M2 — Straightforward, race-free Vulkan baseline

Use FP32 arithmetic and FP32 stage storage initially where device features
allow the chosen formats. Query supported image/buffer formats; have a supported
buffer representation rather than assuming every storage format is mandatory.
Keep stages explicit and use separate destinations so neighboring reads cannot
race with output writes. Record all stages into one GPU command buffer with
proper compute dependencies; do not wait on the CPU between every stage.

Keep RAW ownership until the frame completion fence. Validate against the
independent host oracle, including stage readbacks. A host Vulkan/MoltenVK test
can help iteration but cannot establish Android driver behavior or mobile fps.
Do not replace the shipped photo path or expose the new video option yet.

### M3 — Tiled reconstruction; packing as a measured choice

Build an explicitly derived local-memory reconstruction pipeline using the
public equations. Candidate architecture: guide/low-pass prepass, then tiled
reconstruction with barriers between green, opposite-color and green-site
color reconstruction. Start with camera-linear RGB output. Keep the explicit
multi-stage baseline as the comparison and supported alternative if needed.

Derive each output's full dependency cone. Workgroup barriers synchronize only
that group; read-only source/guide halos must supply all cross-group data. Avoid
multiple workgroups writing the same output texel. Calculate halo overhead,
shared-memory usage and register pressure before choosing tile sizes. Benchmark
64/128/256-invocation candidates that satisfy actual limits; never assume a
1024-thread desktop default is portable or faster.

Compare scalar/paired-site/2×2-cell processing. A four-channel quarter-area
CFA image stores the same number of scalar samples as a one-channel full-area
CFA image at the same precision. For a 3840×2160 region, R16F and quarter-area
RGBA16F both contain about 16.59 MB of sample data. Packing can improve access,
reuse or branching, but it is not automatic fourfold memory/compute reduction.
An extra packing pass may cost more than it saves; include it in measurements.
One avoided full-frame RGBA16F write plus read at 4K is approximately 132.7 MB
of uncompressed traffic per frame, or 3.98 GB/s at 30 fps before cache effects.
That arithmetic motivates investigating tile-local reconstruction; it is not a
measurement of our existing driver traffic or a promised speedup.

### M4 — Precision and output integration

First isolate FP16 storage/quantization changes while keeping FP32 arithmetic.
Only then benchmark optional native FP16 arithmetic, with capability queries,
separate shader variants and explicit quality acceptance. The canonical
`epssq=1e-10` is below the smallest positive IEEE binary16 subnormal (~5.96e-8),
so moving the complete directional math to FP16 can erase a safeguard. Keep
sensitive gradient, division and direction work in FP32 unless another
formulation is separately justified/tested. FP16 image formats and arithmetic
feature support are separate concerns.

Build separate RGB → scaling/grade → P010 first. Preserve full-source detail,
FOV, CFA phase and output chroma/range conventions. A smaller encoded size does
not necessarily reduce the source demosaic footprint. Then investigate final
stage/output fusion with a documented rounding contract, measuring avoided I/O
against added register use/halo work. Test profiles/LUTs separately from demosaic.
Do not copy old backend interfaces or native layout assumptions by convenience.

### M5 — Android acceptance, only when requested

The user stopped device testing during cleanup. Do not run new device tests
now. When authorized later, measure correctness, portability and sustained
cadence on both target GPU families before restoring a visible video RCD choice
or making performance claims. The old recorder's MHC frame-count failure is
separate unresolved evidence; source cleanup did not prove end-to-end recording
acceptance. Distinguish demosaic timings from copy/encoder/mux throughput.

Required production modes are 1920×1080 at 30 fps, 2560×1440 at 30 fps,
and 3840×2160 at 24 fps. These are release acceptance gates, not optional goals.
4K30 is outside the required scope. Keep MHC/Super pixel as working choices
until the replacement passes. See the user-requirements addendum below.

### Legal/provenance gate

Do not promise legal certainty. Establish publicly verifiable sources and
revision history, retain original copyright/license notices, reproduce exact
source/adaptation hashes, and record new code and its authorship. Use one
approved mathematical source and keep removed-source archives out of design,
fixtures and implementation context. Identify this accurately as an attributed
public-source port. Obtain qualified legal review of the actual provenance,
license compliance and existing-dispute implications before representing the
replacement as cleared. Technical tests do not establish legal clearance.
No patent, contract or third-party rights opinion is implied by a GPL header.

### What stable must mean

- Freeze named acceptance devices, sensor route, actual RAW/crop/output sizes,
  codec, profiles, LUT/preview states and thermal/environment conditions before
  claiming acceptance. A result on one phone does not establish all Android
  devices. Verify at least the target Mali and Adreno implementations when the
  user authorizes device tests; identify each device actually tested.
- Run a functional/cadence check per required mode, then at least a ten-minute
  continuous recording per mode on each required device. Include a repeat at
  a warmed but normal operating condition. Extend to longer takes if the user
  needs a longer stability guarantee; ten minutes is measured scope, not proof
  of indefinite operation under arbitrary heat or storage conditions.
- After an explicitly bounded startup period before the recording timeline,
  require zero pipeline drops, zero duplicate/repeated output frames, zero
  frame exceptions, zero starvation and no fallback to another demosaic. Use
  unique frame identities and sensor timestamps, not only encoded PTS.
- Compare captured/encoded distinct frame counts against real capture elapsed
  time. Fixed PTS alone cannot pass: retiming a slower input, duplicating frames,
  speeding up playback or freezing the preview must fail acceptance. Check
  rolling cadence as well as whole-take fps. Whole-second windows should have
  the requested count, allowing at most the mathematically necessary one-frame
  boundary allocation without accumulated deficit.
- Declare sensor/callback jitter limits before running acceptance. Initial
  diagnostic limits: sensor-time p95 gap <= 1.2× nominal and maximum gap <= 1.5×
  nominal, with no lost sensor-frame interval. Codec output reorder/drain is
  assessed separately using decoded frame order/timestamps. Do not loosen limits
  after a failing run without an explicitly reviewed contract change.
- Encode Main10 with audio, decode the complete file, check A/V alignment and
  output metadata, and verify that live monitoring does not change the gate.
  Test each advertised profile and LUT mode before claiming it has passed.
- Preserve full-source reconstruction detail and the specified field of view.
  A lower-quality demosaic, lower-res CFA substitution or undisclosed crop is
  not an acceptable way to meet fps.
- Record every stage and handoff separately. Prefer at least 20% headroom in the
  effective GPU-critical path (approximately 26.7 ms at 30 fps or 33.3 ms at
  24 fps) as an engineering planning target, not a substitute for actual
  end-to-end acceptance or a demand to sum overlapping work incorrectly.
- If any required mode fails, the milestone remains incomplete. Investigate
  scheduling, register spills, memory traffic, copy paths and codec delivery;
  do not relabel failure as an optional performance limitation or quietly
  lower the requested fps.

Device testing remains deferred by the user's current instruction. Research,
provenance, host validation and implementation preparation can proceed, but no
claim of stable Android performance can be made until that gate is measured.
